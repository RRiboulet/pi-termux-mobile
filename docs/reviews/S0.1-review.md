# Review — spike S0.1 (`app/`, `tools/`, ~1463 lines)

**Scope.** `main` @ `d4b4a0e` (the spike) plus `origin/dev` @ `8f3917b` (the
docs commit). Reviewed against `REVIEW_GUIDELINES.md` and `AGENTS.md` in this
repository, and against the artefacts that actually exist on disk:
`tools/rootfs/rootfs.tar` (305,930,240 bytes, built 07:16) and
`dist/pi-android-s0.1-{debug,release}.apk` (built 07:26, and the debug one is
the copy in `/workspace/.artifacts/`).

Three independent reviews were run — a correctness pass and a design pass in
the author's own voice, and an adversarial pass by a model that had not seen the
reasoning. Every finding below was then re-checked against the real files and
the real artefacts; where a reviewer was wrong, that is said.

---

## Verdict

**The spike cannot produce its measurement, and three of the defects compound
into a single failure that no amount of waiting on the phone will resolve.**

The chain is: `make-rootfs.sh` never merges Node into `/usr/local` → the
rootfs has no `/usr/local/bin/node` → the trim that would have removed the
long paths never runs → the archive keeps 246 GNU long-name entries →
`Tar.kt` desynchronises on the first one and the extraction dies at 35% of the
archive → `rootfs-extract` fails → the runner returns early → the report
contains three steps and no numbers.

Even with that fixed, `ProotLauncher.start()` blocks forever on a child
designed never to exit, so the run wedges at `kill-setup` and
`spike-report.json` is never written.

The shape of the spike is right and should be preserved (see *What is right*).
The execution is not, and the gap is roughly **ten small edits** plus one
device run.

## 1. The rootfs has no Node where the runner looks for it — CONFIRMED, on the real artefact

**Where:** `tools/make-rootfs.sh:42-47`

```bash
mv "$WORK/node-${NODE_VERSION}-linux-arm64" "$WORK/usr-local"
mkdir -p "$WORK/usr/local"
if [ -d "$WORK/usr-local" ] && [ ! -d "$WORK/usr-local/bin" ]; then
```

The Node tarball always ships `bin/`, so `[ ! -d "$WORK/usr-local/bin" ]` is
always false, the merge never runs, and the tree stays at `$WORK/usr-local/`.

**Evidence (the shipped artefact, not the source).** `tools/rootfs/rootfs.tar`
contains `./usr-local/bin/node` and an **empty** `./usr/local/bin/`. The runner
execs `/usr/local/bin/node` at `SpikeRunner.kt:237, 254, 272, 299, 333`.
Replaying the script's exact steps reproduces it: the merge is skipped, and the
trim on lines 49-52 — which targets `usr/local/…` — removes **nothing**.

**Consequence.** `node-version` and `node-sqlite-1000-rows` both fail with
"No such file or directory". `docs/S0.8-DECISION-RECORD.md:32` ("Does it
carry `node:sqlite`?") would be answered **no** — a false negative on the
load-bearing unknown of the whole project, which would send Phase 1 down the
custom-bionic-Node road for nothing.

**Fix.** Merge rather than conditionally move, and assert the result:

```bash
cp -a "$WORK/usr-local/." "$WORK/usr/local/"
rm -rf "$WORK/usr-local"
# …then trim, and assert:
test -x "$WORK/usr/local/bin/node" || { echo "FATAL: node missing from the rootfs" >&2; exit 1; }
```

The script already prints `ROOTFS_OK` unconditionally; that line should be
reachable only after the assertion.

## 2. `Tar.kt` desynchronises on a GNU long name — CONFIRMED, and **live**, not latent

**Where:** `app/src/main/java/dev/pidurable/android/Tar.kt:47-48`

```kotlin
'L' -> { longName = readString(gz, size); skip(gz, size); continue }
'K' -> { longLink = readString(gz, size); skip(gz, size); continue }
```

`readString` already consumes the payload; the entry then occupies `size`
bytes **plus block padding**, and the `continue` also bypasses the padding
calculation at the bottom of the loop. The cursor lands at `2 × size` instead
of `size + padding`.

**Evidence (the shipped archive, scanned at byte level).** 246 `'L'` entries.
The first is at offset 107,013,632 with `sizeField = 103`; the correct next
header is 107,014,656, the code reaches 107,014,350 — 306 bytes early, inside
the zero padding. A faithful port of the reader loop, run against the real
archive, dies:

```
parse DIED after 3611 members (2815 regular files), 107015886 of 305930240 bytes consumed
```

35% of the archive. The `usr-local/` subtree — all of Node — is never reached.

> **Correction to one review.** The adversarial pass concluded this was "latent
> on today's inputs" because it checked ubuntu-base and *the trimmed* Node tree
> (zero members over 100 bytes). That is the intended trimming, which the
> script never performs (finding 1). The archive that actually ships has 246
> long-name entries, and the parse dies. Both reviewers' *code* reading was
> right; the severity differed because the inputs were checked, not the
> artefact.

**Consequence.** `rootfs-extract` fails, `SpikeRunner.run()` returns early
(`SpikeRunner.kt:32-41`), and the report holds `environment`, `native-libs` and
a failed `rootfs-extract`. Every measurement is skipped.

**Fix.** Replace the second `skip(gz, size)` with the padding rule the loop
already uses at lines 81-82:

```kotlin
'L' -> { longName = readString(gz, size); val pad = (BLOCK - (size % BLOCK)) % BLOCK; if (pad > 0) skip(gz, pad); continue }
```

**Also, while you are in there** (`Tar.kt`, all confirmed by review):

| # | Defect | Line |
|---|---|---|
| a | `readFully` ends with `return read != 0 && false` — always false. It means "unreadable"; write `return false`. | 133 |
| b | `copyExactly` breaks on a short read without error, so a truncated asset yields silently truncated files. Throw instead. | 139-148 |
| c | A symlink that cannot be created is swallowed, so the extraction can be partly broken and still report success. Count it and put the count in the report. | 66-68 |
| d | `resolve()` permits an empty member name (`out == base`), which is how a desynchronised header becomes `FileNotFoundException: … is a directory`. Reject an empty name. | 61-68 |
| e | Symlink *targets* are never validated — only the link's own path is. A link may point anywhere; only a later write *through* it is caught, and that aborts the whole extraction. Validate the target against the destination. | 66-68 |
| f | **No tests.** The class has no Android dependencies, so a JVM test with a fixture tar built by `tar` on the host can cover traversal, symlinks, hardlinks, long names and truncation entirely off-device. It is the one component with no test at all, and the cheapest risk reduction available here. | — |

## 3. `ProotLauncher.start()` blocks until the child exits — CONFIRMED

**Where:** `app/src/main/java/dev/pidurable/android/ProotLauncher.kt:134-135`

```kotlin
p.inputStream.bufferedReader().forEachLine { }  // drain
p.errorStream.bufferedReader().forEachLine { }  // drain
```

`forEachLine` reads to EOF, i.e. until the child exits. The child it is given
is `killme.js`, whose last line is `setInterval(() => {}, 1000)` — *stay alive
until killed*. The two cannot compose: `start()` never returns.

`run()` (lines 96-106) does it correctly, with two daemon threads. `start()`
is that drain copy-pasted without the threads.

**Consequence.** `stepKillSurvival` (`SpikeRunner.kt:296`) parks the worker
thread inside `start()`, before the readiness poll at line 305 is ever
reached. The `finally` in `SpikeService.kt:52-58` never runs, so
`spike-report.json` is never written and no Downloads copy is made. The run
produces **no report at all** — indistinguishable from "the app never ran".

Secondary deadlock on the same two lines: stdout is drained *before* stderr,
so a child that fills the 64 KB stderr pipe blocks while the caller is blocked
on stdout.

**Fix.** Drain on daemon threads, exactly as `run()` does, and return the
`Process` immediately. Close the child's stdin (`p.outputStream().close()`) so
it sees EOF rather than blocking on a read.

## 4. The kill-ready wait compares nanoseconds against 60,000 — CONFIRMED

**Where:** `app/src/main/java/dev/pidurable/android/SpikeRunner.kt:302-307`

```kotlin
val t0 = System.nanoTime()
var waited = 0L
while (!ready.exists() && waited < 60_000) {
    Thread.sleep(200)
    waited = System.nanoTime() - t0     // nanoseconds, not milliseconds
```

After one 200 ms sleep, `waited` ≈ 2 × 10⁸ ns — far past 60,000. The loop
runs **exactly once**. proot plus a glibc `node` cold start is 1–5 s, so the
ready file will not exist when it is checked.

Finding 3 masks this (the code never gets here), which is why both need
fixing in the same pass: with only finding 3 fixed, `kill-setup` would fail
spuriously on every healthy run.

**Fix.** `val waitedMs = (System.nanoTime() - t0) / 1_000_000`, used in both
the condition and the message.

## 5. `kill-survival` SIGKILLs proot, not the kernel — CONFIRMED

**Where:** `SpikeRunner.kt:327` — `proc.destroyForcibly()`

That kills the process the launcher started: **proot**. The kernel is the
`node` guest *inside* proot, and proot traces its guest with `ptrace`;
killing the tracer detaches the tracee, which keeps running. The guest
therefore survives the "SIGKILL" and goes on holding `/pi/kill.sqlite` open.

**Consequence.** `verify.js` then reopens a database that a **live writer still
holds** — two writers on one WAL database, which is precisely the R5
single-writer violation the plan forbids — and the "survived" verdict is
produced by a process that was never killed. The report claims the kernel was
SIGKILLed when it was not.

**Fix.** Kill the guest. Its host pid is already known: `killme.js` writes
`process.pid` into `/pi/kill.ready` and the runner reads it. Use
`ProcessHandle.of(pid).destroyForcibly()`, confirm `/proc/<pid>` is gone, and
record the pids killed in the report. Add `--kill-on-exit` to `prootArgs` so
a future proot death takes the guest with it — otherwise a wedged run leaves a
stray ptrace pair on the phone that survives the app being force-stopped.

**Also:** `verify.js` gates `ok` on `PRAGMA integrity_check` alone. A reopened
database with **zero rows** — durable writes lost, the exact failure this step
hunts — passes. Gate on the row count as well: `ok: integrityText === 'ok' && count === 1000`.

**Also:** `killme.js` commits 1000 rows and then idles, so the kill lands on a
quiescent process. Make it write continuously so the kill lands mid-write.

## 6. The 16 KB alignment assertion does not check 16 KB — CONFIRMED

**Where:** `tools/stage-native-libs.sh:51`

```bash
if readelf -lW "$WORK/$f" | awk '/ LOAD /{print $NF}' | grep -qvE '^0x[0-9a-f]*000$'; then
```

`^0x[0-9a-f]*000$` matches **any** hex value ending in three zeros:
`0x400` (1 KB), `0x1000` (4 KB) and `0x2000` (8 KB) all pass. The guard
described in the script header, in `AGENTS.md` ("Do not remove that check") and
in the runbook does not check what it claims.

**Why it matters here.** `AGENTS.md` itself records `patchelf` having silently
rewritten an alignment once (`0x4000 → 0x10000`). The next run could produce
`0x1000`, the build would pass, and the APK would carry a `libproot.so` the
device refuses to map — failing at the one step the spike exists to measure,
with a build log claiming the requirement was checked.

**Fix.** Compare numerically against 16384 rather than pattern-matching hex
digits, and also check the APK's own zip alignment (`zipalign -P 16 -c -v 4`),
which nothing in the repository checks today.

## 7. The supply chain is descriptive, not verified — CONFIRMED

- `assets/SHA256SUMS.txt` is **generated from** whatever was downloaded
  (`tools/fetch-assets.sh:43`, `sha256sum … | tee`) and **read by nothing**.
  It is committed, so it looks like a pin. It is a record.
- **The three `.deb` files — the proot binary that runs with the app's
  privileges — have no checksum anywhere.** `stage-native-libs.sh` globs
  `assets/debs/*.deb`, unpacks with `dpkg-deb -x`, patches and stages. The
  committed `libproot.so` cannot be traced to any upstream artefact.
- `tools/fetch-assets.sh:10` reads the Termux index from **`/tmp/p.gz`**,
  which **no script in the repository downloads**. On a clean machine the
  index is missing, every deb fails with `NO PACKAGE`, and the script still
  prints `ASSETS_OK` (line 45) and exits 0. Worse, a *stale* `/tmp/p.gz`
  silently resolves whatever proot version it named.
- `fetch-assets.sh` uses `set -uo pipefail` — **no `-e`** — so a failed
  download still reports success.
- `make-rootfs.sh:17` and `stage-native-libs.sh:26` hardcode
  `/home/vscode/.pi/workspaces/pi-android/assets`, a developer-specific
  absolute path outside the repository.

**Fix, in order of value:** commit the expected hashes *as the input contract*
(including the deb filenames and versions) and `sha256sum -c` them before
use; download the index explicitly; `set -euo pipefail`; print `ASSETS_OK`
only after every verification passes. The tarballs can be checked against
nodejs.org's and Ubuntu's own published `SHASUMS256.txt` rather than a
self-generated file.

*Positive control:* the two committed hashes do match the current upstream
downloads. The manifest is accurate — it simply gates nothing.

## 8. The report is undatable, and an expected failure looks like a real one — CONFIRMED

- **No timestamp, no run id, no build identity, no "sequence complete" flag**
  anywhere in `SpikeReport.kt`. A report from last week is indistinguishable
  from today's, and a partial run is indistinguishable from a complete one.
  For a file that gets filed under `docs/spikes/` and cited by a decision
  record, that is the difference between evidence and hearsay.
- **v3 is expected to fail**, so `failed()` — "any step not ok" — is *always*
  true, and the service always summarises "finished with failures". A reader
  six months later sees a red report on a successful run.
- **The v3 outcome is not classified.** "the exec was denied (EACCES)" and
  "the file was not there (ENOENT)" are indistinguishable, so the cell
  "Is the API-29+ app-home exec ban real?" can be answered from a run where
  the copy never happened. `launch-v3-setup` failing is recorded in a
  *different* step that the decision record does not cite.
- `SpikeState.report` is assigned in the worker's `finally`
  (`SpikeService.kt:56`), so the runbook's "the screen shows each step as it
  completes" is not true today — the screen shows an empty report for the
  whole run.
- The report is written **once**, at the end. A run that dies at step 7 of 9
  produces nothing at all — which is exactly what finding 3 causes.

**Fix.** Add `startedAt` / `finishedAt` / `runId` / `versionName` / APK size
facts; write the report after every step; add an `expected` flag so a met
expectation does not count as a failure; give v3 a tri-state verdict
(`denied` / `allowed` / `inconclusive`) derived from the errno, and let only
`denied` fill the decision cell.

## What is right — do not touch

1. **The shape.** 628 lines of Kotlin is a *measurement harness*, not a product:
   a launcher, a linear sequence of named steps, a JSON report, an untar, an
   FGS, and a screen that only projects the report. No state machine, no
   restart policy, no supervisor, no IPC, no database, no WebView, no
   scheduler. That restraint matches the Phase 0 boundary exactly and is the
   best thing about the change. Do not grow it.
2. **`pb.environment().clear()` before `putAll(env)`** — the spike honours the
   project's own "never inherit the host env" rule, and the child env is small
   and explicit. Do not "helpfully" put the host env back.
3. **The two-thread pipe drain in `run()`** (`ProotLauncher.kt:96-103`) and its
   comment about a child filling a pipe buffer — correct, and the model for
   fixing `start()`.
4. **Three launch strategies, and the reason for three.** Whether the exec is
   permitted is a property of the device's SELinux policy, not something the
   plan may assert; v3 is the control that could invalidate the plan's
   packaging constraint, and the runbook correctly treats a v3 success as a
   *finding*. The count is right; only the reporting of the outcome needs
   fixing.
5. **The report-is-the-product discipline.** JSON out; written to `filesDir`
   *and* Downloads (the only path off a release build); step names the
   decision record cites verbatim; a "how to read the result" table in the
   runbook; a host baseline document. Exactly what `AGENTS.md` demands of a
   spike.
6. **The packaging quartet** — `useLegacyPackaging = true`,
   `android:extractNativeLibs="true"`, `keepDebugSymbols` for `libproot.so`,
   and the plain-`.tar` asset. All four documented, all four present and
   correct.
7. **The Activity has no `android:configChanges` and holds no state** — it
   re-reads `SpikeState` and renders. A cheap, honest rehearsal of "the UI
   never owns progress" and "the Activity is disposable". Keep.
8. **The `native-libs` step** checks symlink-ness, `canExecute` and
   `FLAG_EXTRACT_NATIVE_LIBS` — the packaging fact is *measured*, not assumed.
9. **The `libproot.so` / `libtalloc.so` renaming and the `RUNPATH → $ORIGIN`
   rewrite** — the reasoning in the script header is right and matches
   `AGENTS.md`. Only the alignment assertion is wrong.
10. **Not committing the rootfs, the debs or the APK**, and writing the
    report to a place a human can reach it.
11. **The security and boundary claims.** Nothing in `app/` or `tools/`
    describes proot, the `beforeTool` hook or `android:process` as a boundary;
    the comments consistently say path translation and guardrail, in line with
    the decision record's §6. No overstatement to correct.

## The order I would work in

1. **Fix 1, 2 and 3** — three small edits, and without them there is nothing
   to measure. (1 is a shell one-liner, 2 is a `skip` and a padding, 3 is
   two daemon threads.)
2. **Fix 4 and 5** — otherwise the kill step measures the wrong thing.
3. **Add the verification seam** the design pass asked for, which is the same
   idea as fix 1 seen from the other side: `make-rootfs.sh` must exit
   non-zero unless the produced tree contains exactly the binaries the runner
   is about to exec, and the runner must check the same two paths in the
   *extracted* tree before the launch steps. One mechanism, both sides — and
   it would have caught finding 1 and the whole stale-artefact class.
4. **Fix 6, 7 and 8** — the guard, the pin, and the report's identity — then
   run it on the S21 Ultra per `docs/S0.1-RUNBOOK.md` §1-4.
5. **File the report** as `docs/spikes/S0.1-<date>.json`, and fill §2 of the
   decision record **from that report only**. Cells that were not measured
   stay "not measured" — the two cells cited to S0.1 that the spike does not
   measure (single-writer enforcement, cold start) need either a step or an
   honest "not measured".

Phase 1 should not start until there is a JSON report in `docs/spikes/`.
