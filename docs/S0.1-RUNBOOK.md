# S0.1 runbook — proot on Android (Samsung S21 Ultra, Android 15)

**Target device:** Samsung Galaxy S21 Ultra (SM-S908), Android 15 / API 35, arm64-v8a.
**Question:** can a Node runtime be launched from `nativeLibraryDir`, run a real glibc
rootfs under proot, and use `node:sqlite` — and what does it cost?

This is spike S0.1 from `docs/pi-durable-android-plan.md` §5 R1 / §6 Phase 0. It is the
**go/no-go** for the whole project: if a Node runtime cannot run on the phone, the
architecture in the plan changes (Option B or C1).

---

## 0. What this spike decides, and what it does not

| | |
|---|---|
| **Decides** | Whether a proot rootfs with Node ≥ 22.19 and `node:sqlite` runs inside an Android foreground service, launched from `nativeLibraryDir`, under `targetSdk 35`. |
| **Also measures** | APK size, cold start, proot's syscall-translation overhead, whether the API-29+ app-home exec ban is real, whether the database survives a SIGKILL. |
| **Does not decide** | Whether Gradle can build an APK on the phone (that is S0.7), whether a dev server fits in memory (S0.6), whether OEM killers will park your tasks (S0.3). |

**The one mechanism under test.** On Android 10+ (`targetSdk 29+`), an app may not
`exec()` a file in its own home directory. A Linux rootfs unpacked into `filesDir`
therefore cannot be executed. But `nativeLibraryDir` is *not* in the app home — it
lives under `/data/app/<pkg>/lib/<abi>/` — and with `android:extractNativeLibs="true"`
the package manager puts a **real, executable file** there instead of a symlink into
the APK. `proot` is shipped as `libproot.so` so it is treated as a native library, and
it is `execve()`d from there. Everything in the rootfs then runs *through* proot's
path translation, not by being executed directly.

**If the mechanism fails**, the fallbacks are, in order: a custom bionic Node build →
Option B (Hermes, no shell) → Option C1 (remote execution). See the plan §1.6.

## 1. Before you install — Samsung settings

These are not optional. Samsung's battery management is the single most likely thing to
kill this app (and, later, to park your agent's tasks — plan §5 R3). Menus are named
slightly differently across One UI versions; what matters is the *setting*.

| # | Setting | Where (One UI 7) | Why |
|---|---|---|---|
| 1 | **Never sleeping apps** | Settings → Battery → Background usage limits → Never sleeping apps → **add "Pi Durable Spike"** | Without this, One UI puts the app to sleep and stops its background execution. This is the R3 killer. |
| 2 | **Sleeping apps** | Settings → Battery → Sleeping apps → **remove "Pi Durable Spike"** if listed | The inverse of #1; One UI 7 keeps a separate list. |
| 3 | **Unrestricted battery** | Settings → Apps → Pi Durable Spike → Battery → **Unrestricted** | Stops One UI throttling the foreground service. |
| 4 | **Auto-optimize off** | Settings → Battery → Adaptive battery → **turn off "Auto-optimize now"** | "Auto-optimize" restarts/closes background apps on a schedule. |
| 5 | **Remove from "Rarely used apps"** | Settings → Battery → "Rarely used apps" / Background usage limits | One UI 7 auto-freezes apps you never open. |
| 6 | **Notifications on** | Settings → Apps → Pi Durable Spike → Notifications → **All on** | The foreground service's notification is how you see it is alive. The app asks for the permission on first launch. |

Leave **Developer options → "Don't keep activities" OFF**. The spike wants the Activity
to be destroyed and recreated (that is the "Activity is disposable" invariant), and the
app handles recreation by design — no extra setting needed.

**Play Protect / sideloading.** Installing an unknown app prompts Play Protect. Choose
"More details → Install anyway". On One UI, Settings → Security → **Install unknown
apps** → allow whichever app you transfer the APK with (Files, Chrome, etc.).

## 2. Install the APK

The APK is at `dist/pi-android-s0.1-debug.apk` in this repo (on the host: the repo's
`dist/` folder). It is 83 MB, so pick one of:

### Option A — wireless debugging (no file copy, recommended)

On the **Windows host** (not in this container — the container sits on a Docker bridge
network the phone cannot reach):

```powershell
# 1. On the phone: Settings → About phone → tap "Software information" 7 times
#    to unlock Developer options.
# 2. Settings → Developer options → Wireless debugging → ON.
# 3. Tap "Pair device with pairing code" → note the IP:port and the 6-digit code.
adb pair <phone-ip>:<port>          # type the code when prompted
adb devices                          # the phone appears as <ip>:<port>
adb install -r dist\pi-android-s0.1-debug.apk
```

If `adb` is not on the host: Android Studio's SDK, or the standalone
[platform-tools](https://developer.android.com/tools/releases/platform-tools) zip.

### Option B — copy the file to the phone

Copy `dist/pi-android-s0.1-debug.apk` to the phone (USB cable, cloud drive, whatever you
use), open it with the Files app, and allow the install.

**Use the debug build, not the release build.** The debug build is `android:debuggable`,
which makes `adb shell run-as` work — that is the easiest way to pull the report. The
release build is signed with the same debug key and installs the same way; it just
hides `filesDir` from `run-as` (the report still lands in Downloads).

## 5. How to read the result

### The mechanism (the go/no-go)

| Step | PASS looks like | FAIL looks like |
|---|---|---|
| `native-libs` | `allRealExecutables: true` — `libproot.so` is a **regular file**, not a symlink, and is executable | `isSymlink: true`, or `canExecute: false` → the packaging did not extract the lib. Check `android:extractNativeLibs=true` survived the merge. |
| `launch-v1-exec-nativelib` | stdout contains `PROOT_OK` | `error: java.io.IOException: Cannot run program ...: error=13, Permission denied` → **SELinux denies executing a `system_file` from `untrusted_app`.** Fall back to v2. |
| `launch-v2-exec-via-linker64` | stdout contains `PROOT_OK` | same permission error → the ban is on the *file*, not on the exec path. |
| `launch-v3-exec-from-filesdir` | **FAIL is the expected result** | If v3 *succeeds*, the API-29+ app-home exec ban is not in force on this device, and the whole `nativeLibraryDir` packaging constraint in the plan is unnecessary. That is a finding, not a failure. |

**The v3 result is the most interesting negative.** The plan assumes the ban is real.
If v3 works, the plan's §1.3 packaging requirement can be dropped and the rootfs can be
exec'd directly from `filesDir`, which is simpler.

### The runtime

| Step | PASS looks like |
|---|---|
| `node-version` | `{"v":"v24.22.0",...}` — Node 24 is above the plan's ≥ 22.19 floor |
| `node-sqlite-1000-rows` | `{"ok":true,"rows":1000,"integrity":"ok","journalMode":"wal",...}` — `node:sqlite` works, WAL works, the database is intact |
| `bench-io-cpu` | `usPerStat` is the proot overhead. Compare against the x86 baseline below. |
| `kill-survival` | `{"ok":true,"integrity":"ok",...}` — the database survived SIGKILL |

**x86 baseline** (this container, native Node 24.22.0, no proot) — for scale only, the
architectures differ:

```
cpuMs: 65        (20M iterations)
stat200kMs: 192  (0.96 µs per stat)
write500x1kMs: 8
read500x1kMs: 3
big16mbWriteMs: 5
big16mbReadMs: 8
```

If `usPerStat` on the phone is, say, 5–15 µs, proot's ptrace translation is roughly
5–15× a native syscall and is acceptable for a coding agent. If it is in the hundreds,
proot is too slow and the custom bionic Node build becomes the v1 target.

## 6. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `extractNativeLibs` is false in the report | the manifest attribute did not survive the merge | `aapt2 dump xmltree --file AndroidManifest.xml app-release.apk \| grep extractNativeLibs` — must be `true` |
| `error=13, Permission denied` on v1 **and** v2 | SELinux denies exec of `system_file` from `untrusted_app` | Check `selinuxSelfContext` in the report. Options: (a) try `libproot.so` loaded via `System.loadLibrary` and `execv` from inside the loaded library; (b) build proot as a **bionic PIE** and exec it from `filesDir` as a *non*-app-data file (e.g. `codeCacheDir` or a `noBackupFilesDir` sibling); (c) fall back to Option B/C1. **This is a go/no-go input — record it and stop.** |
| The service is killed after a few minutes | One UI battery management | Re-do §1. Check `Settings → Battery → Never sleeping apps`. |
| `rootfs-extract` fails | the asset is missing from the APK | `unzip -l app-debug.apk \| grep rootfs` must show `assets/rootfs.tar` |
| The app installs but the service never starts | notification permission denied, or the FGS type is rejected | `adb logcat -s AndroidRuntime:E ActivityManager:E` |
| `node-sqlite` fails with `Cannot find module 'node:sqlite'` | the Node build lacks it | Termux's Node is bionic and may not carry it; the official arm64 build does. Re-check which `node` is in the rootfs. |

## 7. After the run

Record the outcome in `docs/spikes/S0.1-<date>.json` (the report itself) and update the
decision record `docs/S0.8-DECISION-RECORD.md`. Then:

- **If v1 (or v2) works and `node-sqlite` passes** → Option A is confirmed. S0.1 is
  **done**; move to S0.3 (the 10× SIGKILL loop) and S0.5 (FGS/alarms on API 30/33/34/35).
- **If the exec mechanism fails but Node works elsewhere** → the custom bionic Node
  build becomes the v1 runtime. That is a week of work, not a rewrite.
- **If neither works** → Option B (Hermes, no shell) or C1 (remote execution). The
  plan records what each costs; the offline requirement is what is lost.
